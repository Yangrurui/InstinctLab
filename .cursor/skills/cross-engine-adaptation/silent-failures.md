# 静默退化故障目录

双引擎打通期间的真实缺陷。收录标准：**没有异常、没有失败的测试、训练照常收敛**。按「为什么没有信号」分类——可迁移的是这个，不是具体字段名。

| # | 缺陷 | 无信号的原因 | 实际发现路径 |
|---|---|---|---|
| 1 | 接触传感器漏声明 `found` | 引擎内部另有消费者 | 与参照对回合长度曲线（5000 轮后） |
| 2 | 接触元素解析没缓存 | 纯性能，数值全对 | GPU 利用率 1%、墙钟 |
| 3 | 环境从未播种 | 默认值的含义是「不做」 | 逐行读两个参照的入口脚本 |
| 4 | TF32 开关只随了一个参照 | 共享入口二选一 | 同上 |
| 5 | 星号导入遮蔽正版奖励 | 急切绑定优先于惰性查找 | 尝试删除退役层 |
| 6 | Gym id 无人注册 | 副作用改显式函数，调用点没跟上 | 同上 |
| 7 | golden 出自无法实例化的配置 | 参照从没被真的构造过 | 同上 |
| 8 | 白名单 11 条死条目 | 检查通过 ≠ 检查有效 | 新增过期检测 |
| 9 | entry point 指向不存在的模块 | 惰性引用不被解析就不证伪自己 | 清点存量任务时逐个核对 |
| 10 | `preserve_order` 在 `.*` 下是空操作 | 对拍前的归一化抹平了待验证的性质 | 顺着「这条是否真的实现了」逐层查代码 |

## 1. 引擎内部还有别人读这个字段

**症状**：mjlab 接触传感器 `fields` 默认 `("found", "force")`，我们只声明 `("force",)`——`force` 确实是力历史要读的那个。结果 `illegal_contact` 永不触发、`feet_air_time` 恒付零，回合只能超时结束。

**为何无信号**：传感器构造成功，环境正常 step，策略照常收敛。mjlab 的空中/接触计时是从 `found` 累加的，缺了它 `_update_air_time_tracking()` 直接 return——**静默 return，不抛异常**。

**怎么发现的**：跑满 5000 轮，与 InstinctMJ 对回合长度曲线。参照 10.5→47→646→991，我们从头到尾恒定 1000.0。

**规则**：给引擎传字段清单时，禁止只写「这一层要读的」。**覆盖引擎默认值前先 grep 它内部还有谁读这个字段。** 默认值往往是多个消费者需求的并集。

**衍生信号**：只在 reset 那步产出的日志（mjlab 每步清空 `extras["log"]`，Isaac Lab 只在 `_reset_idx` 清）在终止失效时会被 wrapper 补零成一片 `0.0000`。**满屏精确的 0.0000 是信号不是噪声。**

## 2. 纯性能退化，数值全对

**症状**：Isaac 侧环境慢十倍（56,339 → 5,699 step/s，4096 env），GPU 全程空转、CPU 120%。

**为何无信号**：所有数值断言照常通过，`compare_terms.py` 修复前后结果**完全相同**。这类退化在数值维度上不存在。

**根因**：`ContactSensorRef` 的元素解析没缓存，每步付三次 `ContactSensor.body_names`——那是个每次访问都从 physics view 重建的 property，单次约 70 毫秒，占掉 21.6 秒里的 18.7 秒。Isaac 自己的 term 不付这笔钱，是因为 `SceneEntityCfg` 由 manager 解析一次；而 `ContactSensorRef` 由 term 解析（这正是它能同时对上 Isaac 一个宽传感器和 mjlab 几个窄传感器的原因），manager 白送的缓存就得自己做。

**规则**：**跨引擎间接层的每一次运行时解析，都要问它在原生实现里是不是初始化期做完的。** 是的话这层必须自己缓存。间接层天然会把「解析一次」变成「每步解析」，因为它下沉到了更细的粒度。

## 3. 默认值的含义是「不做」

**症状**：训练一切正常，只是不可复现。

**根因**：两个引擎的 `cfg.seed` 默认都是 `None`，含义是**完全不播种**。入口只调 `torch.manual_seed` 不等价——它在环境构造之前，且不覆盖 numpy/random。

**为何无信号**：没有任何异常或断言会响。不可复现本身不产生错误。

**规则**：读默认值时区分「默认值是个合理的数」和「默认值的含义是关掉」。后者必须显式设置。修复是 `compiled.env_cfg.seed = agent_cfg.seed`。

## 4. 两个参照互相矛盾，共享入口被迫二选一

**症状**：无论怎么写，必有一侧不在它参照的栈上跑。

**根因**：main 显式开 TF32 matmul 与 cudnn 设置，InstinctMJ 什么都不设。写进共享 `train.py` 就必然有一侧不是它的参照。

**规则**：**两个参照互相矛盾的设置，禁止在共享入口二选一，必须下放到各自适配器的 `bootstrap`。**「复现一次参照训练」包含复现它跑在什么栈上——数值后端开关属于栈的一部分。

## 5. 星号导入静默压过正版

**症状**：main 的任务完全构造不起来，而所有测试和对拍照常通过。

**根因**：`mdp/__init__.py` 的 `from .unified import *` 遮蔽了 main 的奖励实现。退役层的重实现**算术忠实、签名不同**，manager 构造期直接拒绝。星号导入**急切绑定名字**，优先于下面的 `__getattr__` 惰性查找。

**为何无信号**：没有 import 错误，没有测试会响——测试导入的是同一个被遮蔽的名字。

**规则**：**退役一层不等于停止使用它。** 只要还有 `from .retired import *`，被退役的实现就仍是活的且优先。已由 `tests/test_parity_static.py` 禁止该文件出现星号导入。

**这个模式在 parkour 仍然活着**：`tasks/parkour/mdp/__init__.py` 有七层星号链，实测 `joint_torques_l2` 在 `isaaclab.envs.mdp` 与 `instinctlab.envs.mdp` 各有一份、后者静默胜出。今天良性（默认行为一致），但**专门调查这份代码的 agent 把它标成了「来自 Isaac Lab」——标错了**。绑定关系读不出来就是危害本身。详见 [repo-tasks.md](repo-tasks.md)。

## 6. 副作用改成显式函数，调用点没跟上

**症状**：`gymnasium.error.NameNotFound`，入口连自己的 task id 都找不到。

**根因**：`tasks/__init__.py` 为了引擎无关，停止在 import 时注册 Gym id、改提供 `register_legacy_isaac_tasks()`，但 main 的 `train.py` 仍写着 `import instinctlab.tasks  # noqa: F401`，全仓库无人调用新函数。

**规则**：**包为了引擎无关而把副作用改成显式函数时，要同时改掉所有依赖那个副作用的调用点。** `# noqa: F401` 的裸 import 就是「我依赖这个 import 的副作用」的标志，是搜索起点。

## 7. 参照从没被真的构造过

**症状**：golden 是从一份无法实例化的配置里 dump 的（缺陷 5 的下游），而所有验收照常通过。

**为何无信号**：我们对 main 做了逐字段比对、静态不变量、白名单过期检查，唯独没有「把它建起来跑一步」。**一把连不上电的尺子，量什么都是准的**——尺子坏了，被量的东西和尺子一起错，diff 依然为空。

**规则**：**参照实现必须有人定期真的构造一次并 step。** 这是唯一能发现「尺子本身坏了」的检查，且不能用任何静态手段替代。

## 8. 检查通过 ≠ 检查有效

**症状**：白名单里 11 条死条目，其中一条项级前缀条目理由早已过时、却仍覆盖着整个奖励项——那个项下的任何新差异都会被静默吃掉。

**规则**：**白名单条目必须会过期。** `verify.structure.unused()` 报出解释了零处差异的条目即失败。抑制机制（白名单 / skip / 容差）必须自带反向检查，否则它们只会单调增长并逐渐吞掉真实差异。

## 9. 惰性引用的正确性只在被解析时才检验

**症状**：`tasks/shadowing/whole_body/config/g1/__init__.py` 的 `rsl_rl_cfg_entry_point` 指向 `rsl_rl_ppo_cfg:G1ShadowingPPORunnerCfg`，而该模块不存在。**从不报错**——仓库已统一到 `instinct_rl`，没有任何代码去解析这个 entry point。

**为何无信号**：坏引用不会主动证伪自己，只有被解析时才会。

**为什么这条特别重要**：本项目为了引擎隔离，**刻意到处使用惰性引用**——`engines.ADAPTERS` 与 `tasks.registry.TASKS` 存点路径不 import 被注册者、`AgentSpec.runner` 用 `"pkg.module:Class"` 由 backend `resolve()`、`mdp/__init__.py` 用 `__getattr__` 延迟查找、`CompiledTask.agent_cfg` 惰性解析。这些设计是对的，但**隔离技术本身制造了一类未经检验的引用**。

**规则**：每加一处惰性引用，就加一个把它**全部解析一遍**的测试。枚举注册表里每个点路径并 import 它，比等到有人真的选中那条路径便宜得多。

跨引擎栈已经这么做了——`tests/test_train_entry.py::test_every_registered_engine_resolves_to_an_adapter` 会把 `engines.ADAPTERS` 逐个解析。**坏引用出现在 legacy 那一侧，正是因为那一侧没有这个测试。** 适配存量任务时把这类测试一并补上。

## 10. 开关在这个参数下是空操作，而三处文档声称它生效

**症状**：D1 要求关节轴统一为 DFS 序。任务写的是 `EntityRef("robot", joints=".*", preserve_order=True)`，读起来完全像是把顺序钉住了。实际上 Isaac 侧留在 PhysX 的 BFS 序、mjlab 侧留在模型文件顺序，两者都不是 DFS，也不是同一个排列。

**为何无信号**：`resolve_matching_names` 按**模式**的先后排列选择结果。只给一个 `.*` 时所有关节都落在同一个模式里，模式内部仍按实体自身顺序排——`preserve_order` 真假**结果完全相同**。这个标志在这个参数下没有任何效果，而它的名字读起来正相反。

**为何全套验收都看不见**：

- `test_asset_parity.py` 比的是关节名的**集合**，顺序不在比较范围内。
- `probe_terms.py` 逐值对拍前会先把两边**重排到 canonical 序**再比——重排之后无论原始顺序如何都一致，检查对它想验证的东西天然免疫。
- `check_mjlab.py` 有一条 `action order matches the catalog's depth-first order` 断言，但 mjlab 资产是从 `RobotSpec` 按 DFS 推导的，这条断言在 mjlab 上恒真、是空转的。Isaac 侧没有对应断言。
- 单引擎训练完全正常：观测与动作跑在同一个原生序上，学习问题只是做了个置换，照常收敛。

**三处声称它已生效**：两个引擎 `terms.py` 里 action builder 的 docstring，以及白名单里 `actions.joint_pos.preserve_order` 那条理由——它把一个零效果的差异解释成「这就是 D1 的落点」。**白名单理由也会说谎，而且没人复核它。**

**规则**：

1. **断言开关的效果，不要断言开关的取值。** 把 `preserve_order=True` 写进白名单不构成任何保证；要断言的是解析出来的名字序列等于 canonical 序列。
2. **对拍前做的任何归一化，都会让检查对它归一化掉的那个维度失明。** `probe_terms.py` 的重排是必要的（写状态要转成引擎序），但读取侧的重排把「两边是否对齐」这个待验证的性质直接抹平了。归一化步骤必须问一句：它抹掉的是噪声，还是我要验的东西？
3. **在两边恒真的断言等于没有断言。** mjlab 那条 DFS 检查因为资产从 canonical 推导而永远为真，看起来覆盖了 D1，实际只覆盖了不会出错的那一侧。

修复后两引擎的 `joint_pos` / `joint_vel` / `actions` 实测差为**精确的 0**，且去掉重排后这个对拍才第一次真的在检验对齐。

## 11. 写得像断言、但永远不会失败的检查

**症状**：某个性质「有检查」，出问题时那个检查照常通过、脚本照常退出 0。

**这一类已经出现三次，形态各不相同**，所以值得单独列：

| 位置 | 长什么样 | 为什么不会红 |
|---|---|---|
| `check_mjlab.py` 的 D1 检查 | `print(f"action order matches...: {names == catalog}")` | 是 `print` 不是 `assert`。它把布尔值印出来，然后继续往下走，脚本末尾固定 `return 0` |
| `test_no_reward_is_missing` | `assert set(golden) - set(task) == set()` | 单向差。任务多长出一个奖励，优化目标变了，这条照过 |
| `reference_mjlab.scene_sensors()` | 一个完整的提取器 | 没有任何调用者。读代码的人会以为传感器比过了 |

再加两种同样常见的：

- **参数化列表来自一个可能为空的来源**：`@pytest.mark.parametrize("engine", sorted(selector_kinds()))`——注册一旦不发生，收集到零个用例，整份文件绿着通过。凡是 parametrize 的来源是运行期计算的，都要另加一条「来源非空且等于预期集合」的断言。
- **辅助断言恒真**：`assert isinstance(ast.parse(src), ast.Module)`——`ast.parse` 只会返回 `Module`。这种行看起来在加固，实际是噪音。

**规则**：

1. **诊断输出和验收断言要分清楚。** 一个打印布尔值的 `print` 读起来像检查，行为上不是。跨引擎不变量所在的位置，必须能让脚本以非零码退出。
2. **集合比较默认写成相等，要写成单向差就得说明为什么单向是对的。**
3. **提取器没有调用者就是死代码**，而且是有害的死代码——它让人以为这块比过了。要么给它加断言，要么删掉。
4. **检查通过时说一句话。** 静默通过和没有执行长得一模一样。`check_parity.py` 的 golden 复核会在没有差异时明确打印「golden 仍与 main 的配置一致」，就是为了这个。
5. **判断一个检查有没有用，唯一可靠的办法是把它保护的东西改坏，看它红不红。** 本轮所有新加的检查都做了这个变异实验；`test_the_joint_axis_is_pinned_to_the_canonical_order`、选择器注册守卫、接触分组断言、回合长度检测都验证过会红。

## 12. 尺子自己过期，而所有检查都对着尺子

**症状**：验收全绿，但它比对的基准早已不再描述它声称记录的那个东西。

**根因**：`check_parity.py` 把编译产物与 `golden.json` 逐字段比对，而 `golden.json` 是某一次从 main 的 `G1FlatEnvCfg` dump 下来的快照。**没有任何检查反过来验证这份快照仍然等于 main 的当前配置**。main 改了、或者 main 一度根本构造不起来，golden 都会安静地继续充当基准——事实上这个项目的 golden 确实曾经是从一个坏掉的状态 dump 出来的（见第 9 条）。

**规则**：凡是「把活的东西 dump 成文件、之后都跟文件比」的验收，必须有一步**把文件和活的东西重新比一次**。`check_parity.py` 现在默认会重新实例化 main 的配置并与 golden 对照，不一致就报出该重跑哪条 `dump_golden.py` 命令。同理，`--construct`（真的把编译产物建起来并 step）也从可选开关改成了默认——它长期是可选的，等于常规使用中从没人跑过它。

## 13. 尺子被改去迎合被测物

**症状**：验收全绿，而且这次 golden 确实是从「当前的 main 配置」dump 的、复核也通过——但那份 main 配置本身被本地改过。

**根因**：比第 12 条更隐蔽一层。第 12 条是尺子过期，这里是**尺子被主动弯折**。`engines/isaacsim/scene.py` 的 `PROFILE_DEFAULTS` 写着 `self_collision: True`，注释声称「matching main's values」，而 main 其实是 `False`。当初对拍必然报过这处差异，而它被解决的方式是：把编译器那段 `spawn.replace(...)` 原样复制进 `G1FlatEnvCfg`——也就是 golden 的源文件本身。共 22 行。此后两边永远相等。

代价是双重的：一，「Isaac ≡ main」这句话此后再无内容，因为参照已经不是 main；二，0 卡上那次训练实际带着 URDF 自碰撞导入在跑，与 main 的物理不同，而没有任何东西会提示这件事。**四轮独立审计逐行读过这个文件，无一发现**——因为改后的文件本身完全合理，看它一百遍也看不出它不是 main 的。

同一个根因的第二种形态：那 22 行里其余 21 行**是资产数值的逐字复制**（`solver_position_iteration_count=8`、`max_depenetration_velocity=1.0` …），与 `G1_29DOF_TORSOBASE_POPSICLE_CFG` 声明的一模一样。复制当天无害，所以没人反对；它的危害是把「资产说了算」变成了两个数据源，资产一改就静默分叉。现在这些键默认 `None` 表示「沿用资产」，只有任务显式声明才覆盖。

**规则**：

1. **参照必须来自参照，不能来自记忆或副本。** 凡是声称「这个文件就是上游/release 的」，就得有一条检查去问上游。`tests/test_main_reference.py` 直接 `git show main:<path>` 逐字节比，并且把有意改动的文件单列一张表、断言它们**确实还不同**（否则条目自身过期）。

   **手抄参照还会顺带把比较变成单向的**，这是它最不显眼的代价。`tests/test_agent_cfg.py` 曾把 main 的 22 个超参转写成一张 `MAIN` 表，两个测试都是「遍历 MAIN，在配置里查到并比对」——于是配置里**多出**一个 main 没有的超参完全隐形，训练会静默用上参照没有的旋钮。手抄的表天然只能这样用：你没有 main 的全集，就写不出对称断言。改成用 `git show main:` 把那份文件整份执行起来（只替换它唯一的 `configclass` 导入，而 vendored 的 configclass 另有测试逐函数钉住），一句 `declared == mains` 同时覆盖改值、丢字段、多字段三种情况，且不再需要维护任何表。
2. **对拍报出差异时，先问「哪边错了」，不要默认是实现对、参照错。** 修参照是允许的，但必须是「参照本来就写错了」，不能是「改了参照能让检查变绿」。
3. **不要把另一处数据的值复制成默认值。** 用「未声明」的哨兵（`None`）表示沿用来源，让来源保持唯一。默认值里出现一个和别处相等的字面量，就是一次未来的静默分叉。

## 有信号的对照组

不是所有缺陷都静默。这两个被常规手段抓住了，可作为「什么时候能省事」的参照：

- **根部速度写入的参考系错配**：Isaac 收质心速度、mjlab 收连杆速度，同样的数写进去两个机器人不在同一状态（实测连杆速度差 0.85 m/s），随后**所有速度类 term 全部不一致**。逐值对拍立刻炸。因为它污染了状态本身，下游全线可见。
- **事件 `interval_range_s` 未透传**：这个介于两者之间——一切照常构造，只是周期性推力永远不触发。属于第 1 类（配置字段漏传，无异常），靠逐字段对拍抓住。

分界线：**污染状态的错误有信号；只影响「某件事发生的频率或时机」的错误没有信号。** 后者包括接触计时、事件触发、终止条件、curriculum 推进——全部落在时间轴上，单点比对结构性地看不见。

## 写新代码时怎么先发制人

在写下每一处跨引擎适配代码时问：

1. 我覆盖了引擎的哪个默认值？**它内部还有谁读这个字段？**
2. 这个量存在于时间轴上吗（计时、计数、频率、触发）？是的话单点对拍看不见它，必须补行为探针或曲线。
3. 这次运行时解析，原生实现是不是初始化期做完的？
4. 这个默认值的含义是「一个合理的数」还是「关掉」？
5. 我依赖了哪个 import 的副作用？
6. 我加的这处惰性引用（点路径 / entry point / `__getattr__`），有没有一个测试会真的解析它？
7. 我在对拍前做的归一化（重排 / 排序 / 取集合 / 容差），抹掉的是噪声还是我要验的那个性质？
8. 我断言的是开关的**取值**还是它的**效果**？取值相等不代表效果发生。
9. 我的参照，最近一次被真的构造起来是什么时候？
10. 我刚写的这个检查，**把它保护的东西改坏，它会红吗**？没做过这个实验就不算写完。
11. 这是 `print` 还是 `assert`？脚本会因此以非零码退出吗？
12. 我比对的基准是一份文件吗？**谁负责发现这份文件已经过期**？
13. 我改了某处实现之后，有没有别处的注释/文档还在描述改之前的行为？（本轮就有两处是自己改出来的）
14. 我这个默认值/常量，是不是另一处数据的复制？**谁保证两边一起改**？能沿用来源就别复制。
15. 对拍报差异时我改的是实现还是参照？如果是参照——它凭什么是错的？（「改了就绿」不是理由）
16. 我声称「这个文件是 main 的」，有检查真的去问过 main 吗？
